# Changelog

## 2.0.13

From installing 2.0.9–2.0.12 in a Quarkus/Maven repo with a root module plus separate Maven projects in subfolders.

- **Staged-only pre-commit keeps the merge.** `HARNESS_HOOK_STAGED_ONLY=1` checked the staged snapshot in a fresh worktree with no `MERGE_HEAD`, so when the commit was a merge, repo logic that checks `git rev-parse -q --verify MERGE_HEAD` (merge-aware test selection, a base that switches during merges) saw an ordinary commit and counted everything the merge brought in as changed. The real `MERGE_HEAD` is now written into the scratch worktree, and goes with it.
- **gate-proof.sh plants its test in the root module.** The JUnit 5 picker took the first `src/test/java` file in `git ls-files` order, so a nested project (`face-service/src/test/java/…`) that the repo's test command never runs came before the root's `src/test/java/…`, and the proof ended inconclusive. Root-module test files now come first, and `HARNESS_GATE_PROOF_BESIDE=<existing test file>` plants the test beside a file you choose.
- **`make help` prints any description.** Descriptions went into single quotes as-is, so an apostrophe ("the branch's changes") was a shell syntax error and `make help` failed. They are now escaped (`harness_sq`). The harness.mk header says a repo may set `_HELP_<target>` after the include to describe what its targets really do.
- **HARNESS_TEST_SECS is data.** check-fast put its value into a shell test at parse time, so `make check-fast HARNESS_TEST_SECS='1" ]; <cmd>; [ "'` ran `<cmd>`. Only a digits-only value reaches the shell now; anything else counts as unset.
- **Exact allow rules for make.** harness-init's settings question and the file reference suggested `Bash(make check:*)` / `Bash(make test:*)`. make takes variable overrides and harness.mk runs `HARNESS_*` variables as recipes, so such a prefix also pre-approves `make test T=x HARNESS_TEST_ONE='<any command>'`. They now suggest `Bash(make check)`, `Bash(make check-fast)` and `Bash(make help)`. The shipped `claude-settings.json` has no allow rules and is unchanged; check a committed `.claude/settings.json` for prefix rules by hand.
- **red-proof.sh and diffscan.py use the repo's base.** With no argument, both compared with `origin/HEAD` (diffscan: `HARNESS_BASE` from the environment, which harness.mk never exports). On a repo whose features branch from `dev`, the merge-base with `origin/main` was thousands of commits back: red-proof put thousands of unrelated production files back and reported a false red or inconclusive, and a `"scope": "diff"` sensor scanned every commit since `main` as new code. Both now ask the repo as the stop gate does, through one shared helper, `cmd.sh <dir> --base`: the `harness-base` target, then `HARNESS_BASE`, then `origin/HEAD`, `origin/main`, `origin/master`. The stop gate uses the same helper.
- **Per-worktree ports from the compose file.** setup.sh assigned ports only for `*_PORT` keys in `.env.example`. A repo without one (an `env.template`) whose compose file binds `${LOCAL_PG_PORT:-5442}` got the same port in every worktree, so a second worktree's `docker compose up` failed with "port is already allocated". Keys used as `${NAME_PORT:-<port>}` in the compose file are now assigned the same way and written to `.env.local`; the main checkout keeps the key's `.env` value, else the compose default, while it is free. A `${NAME_PORT}` without a default is set elsewhere and left alone, and `.env.example` keys behave as before.
- **pre-push can check exactly the pushed commit.** It runs `check` on the working tree, so a broken commit fixed but not committed passed and was pushed, and an uncommitted half-edit blocked a good push. It now says so when uncommitted or untracked code is part of the run, and `HARNESS_HOOK_STAGED_ONLY=1` (the pre-commit switch) runs `check` on the pushed commit alone in a scratch worktree (new `.githooks/snapshot.sh`, shared with the staged-only pre-commit). It is opt-in: the scratch worktree links only `node_modules`, `.venv`, `.env` and `.env.local`, so a `check` that needs other gitignored files (local config, generated code) or warm build output fails there. Without `snapshot.sh` (an upgrade that only refreshed) it checks in place.
- **Headless tip:** the `--allowedTools` example in the user guide pre-approved `Bash(make *)`, the same hole as above; it now lists the exact make commands.
- **The Bash guard refuses SKIP_HOOKS however it is set.** It caught `SKIP_HOOKS=1` only as a prefix on the `git` command itself, so `export SKIP_HOOKS=1 && git commit`, `export SKIP_HOOKS=1; git push` and `declare -x SKIP_HOOKS=1` got through and both hooks skipped. Any assignment of `SKIP_HOOKS` (prefix, `env`, `export`, `declare`, a bare `SKIP_HOOKS=1;`) is now denied; `HUSKY` and `SKIP` are denied when the same command line runs git. An internal guard error now asks instead of allowing.
- **The gate is harder to switch off through init-state.json.** The git hooks skip ("setup in progress") while `.harness/init-state.json` lacks `"gate_wired": true`, and that file is gitignored and was unguarded, so an agent blocked by a red gate could write `{}` there. Once the gate is wired, the file guard denies an Edit or Write after which the hooks' own test (`"gate_wired": true` on one line) no longer matches, and the Bash guard denies shell writes to the file (redirect, `tee`, `cp`/`mv`, `sed -i`, also after a `cd`) and asks for a write through a variable or glob, or an inline `python3 -c`/`node -e` that may write it. Reading the file (`jq`, `cat`, `json.load`) is unaffected. Best effort: a script file that writes it is not inspected. harness-init and harness-upgrade only ever set it to `true`; `gate-proof.sh` and `migrate.py` write it from inside scripts and are unaffected.
- **Stop gate: Docker missing is environmental too, and only Docker's own errors are.** Besides a stopped daemon, Testcontainers' `Could not find a valid Docker environment`, `docker: command not found` and `command not found: docker` now warn instead of blocking. `setup error` counted anywhere in the output, so a test named `…setup error…` turned a real failure into a warning; it now counts only at the start of a line, optionally after the target's name (`setup error: no base branch`, `typecheck: setup error: …` as a make recipe prints it), which a repo's gate can print for its own setup problems. Free text such as a skip reason `requires docker` next to a real failure no longer softens it. Documented in the stop-gate header, the README and the user guide.
- **A setup step can report "needs you".** setup.sh knew only ✓ (exit 0) and ✗, so a `setup-services` that prints "needs you: no DB_JDBC_URL in .env" and exits 0 (a fresh clone must still pass setup-proof) showed `services ✓ … needs you: none`. A line `needs you: <what>`, optionally prefixed `<target>: `, is now added to "needs you" with the target name, and the step shows `✓ (needs you)`. Exit codes are unchanged. The step's output is copied through a `tee` that setup does not wait for, so a process the step leaves running (a server, a watcher) can't stall setup, and it runs with `PYTHONUNBUFFERED=1` so a long Python step's lines show as they happen. A deps step that reports "needs you" no longer also triggers the maven-credentials hint.
- **A repo with its own git hook keeps it.** A repo whose `.githooks/pre-commit` is its own (migration checks, say) had the plugin hook copied in as `.githooks/harness-pre-commit` by hand: `assets.py` still tracked `.githooks/pre-commit`, reported it "modified" forever and never refreshed `harness-pre-commit`. Now, when the repo's hook isn't a plugin copy (or `harness-pre-commit` exists), `assets.py` installs, tracks and refreshes the plugin hook as `.githooks/harness-pre-commit` (same for `pre-push`) with `snapshot.sh` beside it, drops the repo's hook from `assets.json`, recognises a hand-copied released version as stale, and, while the repo's hook doesn't call it, prints how: `HARNESS_GIT_HOOK=1 bash "$ROOT/.githooks/harness-pre-commit" || exit 1`.
- **Hooks without snapshot.sh check in place.** An upgrade that refreshed the hooks but never installed `snapshot.sh` made `HARNESS_HOOK_STAGED_ONLY=1` fail every commit and push; both hooks now say it is missing and check the working tree.
- **`HUSKY=0 npm ci && git status` is allowed.** A `HUSKY`/`SKIP` prefix on another command denied any git later in the same line; a prefix now counts only on the git command itself (`SKIP_HOOKS` still counts anywhere).
- **The guards fail closed without python3.** With no `python3` both guard hooks allowed everything silently. The Bash guard now asks for a command that may skip hooks, change git history, delete, or write a file the harness protects (a word match using only bash builtins), the file guard asks for an edit to `.env*`, `CLAUDE.md`, `INVARIANTS.md`, `init-state.json` or `harness-workspace.json`, and the session is told once.
- **A script that writes init-state.json asks.** Running a script file (`bash f.sh`, `python3 f.py`, `./f`) whose text names `.harness/init-state.json` asks once the gate is wired; the harness's own scripts (`scripts/harness/`, the plugin's) are exempt. Names one level deep only.
- **`HARNESS_TEST_PLAN` keeps lint's coverage warning with a custom runner.** `HARNESS_TEST_CHANGED_CONFIRMED = 1` silenced "check-fast tests nothing for <file>" along with the custom-runner warning, so a repo with its own selector lost its only warning about changed code no test covers. A repo can set `HARNESS_TEST_PLAN` to a command that gets the changed files and prints `none: <file>` for each one its runner would test nothing for; `make harness-test-plan` and harness-lint use it like related-tests.sh's dry run.
- **`make help` stops saying "all tests".** `check` and `test` run `HARNESS_TEST_ALL`, which a repo may point at its own selector; the default help now says "test (as configured: HARNESS_TEST_ALL)" so repos need no `_HELP_` overrides to keep it true.
- **pre-push checks the commits git pushes.** With `HARNESS_HOOK_STAGED_ONLY=1` it checked HEAD, and a push of another branch (`git push origin other-branch`) was skipped. It now reads each pushed local sha from git's ref lines and checks that commit in a scratch worktree, so the verdict is about what is pushed, whatever is checked out. In place (the default) a dirty tree prints pre-commit's warning ("unstaged or untracked changes are part of this check", naming the opt-in), a clean tree prints nothing extra, and another branch is skipped with a message naming the opt-in.
- **harness-lint warns on a moving plugin pin.** A github marketplace source has no sha field, so `extraKnownMarketplaces.agent-harness.source.ref` is the only pin. A branch or a missing ref installs whatever is pushed there next as every teammate's hooks; lint now warns unless the ref is an exact `vX.Y.Z` tag. harness-init and harness-improve write the ref as the plugin's version.
- **Release tags never move.** New `docs/RELEASING.md`: a fix ships as a new patch version, never a re-tag; the repo ruleset "protect release tags" blocks updating or deleting `v*` tags.
- **Docs:** README and user guide list the two lines a repo's targets can print (`setup error:` from check-fast, `needs you:` from a setup step) and describe pre-push's two modes: the working tree in place (fast, warm build, uncommitted code can change the result) or, with `HARNESS_HOOK_STAGED_ONLY=1`, exactly the pushed commits (scratch worktree, cold build). The team-rollout docs say the marketplace `ref` must be an exact tag.
- **Upgrade:** `/agent-harness:harness-upgrade` refreshes `harness.mk`, `gate-proof.sh`, `red-proof.sh`, `setup.sh`, `sensors/lib/diffscan.py`, `scripts/harness/cmd.sh`, `scripts/harness/lint.sh`, `.githooks/pre-commit` (or `harness-pre-commit`) and `.githooks/pre-push` (unmodified copies) and installs `.githooks/snapshot.sh`. No migration; tested from 2.0.9, 2.0.10, 2.0.11 and 2.0.12 installs.

## 2.0.12

From a review of the harness install in a repo on 2.0.9 whose features branch from `dev`.

- **red-proof.sh compares with the fork point.** An explicit base (`red-proof.sh origin/dev`) was used as-is, so commits `dev` gained after the branch forked counted as "production code changed" and were checked out into the scratch worktree: a mixed tree and a wrong verdict. Now any base is turned into its merge-base with HEAD, as the default already was.
- **Git hooks fail closed on a broken gate.** When `make -n check-fast` failed (a Makefile syntax error, a bad `$(shell …)`, a missing include), `cmd.sh` exited 3 and both hooks skipped silently. They now skip only while there is nothing to resolve the gate from and init never wired it; otherwise they print make's error and `Run make -n check-fast (check)` and exit 1.
- **pre-commit and the staged snapshot.** check-fast tests the working tree, so unstaged edits could block a good commit or let a broken one through. pre-commit now warns when unstaged or untracked code is part of the run, and `HARNESS_HOOK_STAGED_ONLY=1` runs check-fast on exactly what is staged (a scratch worktree from `git write-tree`, with `node_modules`, `.venv` and `.env` linked). Opt-in, because build output starts cold there.
- **pre-push tests only what it pushes.** It reads git's ref lines and runs `check` only when a pushed ref is the checked-out HEAD: tag pushes, branch deletions and pushes of another branch skip with a message. `SKIP_HOOKS=1` now skips both hooks (people only; the Bash guard still refuses it for agents).
- **Stop gate: the repo's base, this session's changes.** The base came from `HARNESS_BASE` or `origin/HEAD`, so on a repo whose Makefile picks `dev` per branch every `dev` checkout looked thousands of commits ahead and check-fast ran at the end of every turn. The gate now asks the repo (new hidden target `make harness-base`, cached per HEAD and branch in `.harness/base-cache`), then `HARNESS_BASE`, then `origin/HEAD`. The session hook records a code fingerprint in `.harness/session-<id>` at start (kept across resume and compaction), and the gate runs only when this session changed code: investigating with scratch files left from before no longer triggers it. A check-fast that fails because the environment is down (`Docker is not running`, `Cannot connect to the Docker daemon`, `setup error`) warns instead of blocking. `HARNESS_STOP_GATE=0` still turns it off.
- **`HARNESS_TEST_CHANGED_ARGS`** (default `$(CHANGED)`) is what check-fast passes to `HARNESS_TEST_CHANGED`. A repo whose runner picks its own tests sets it empty, and check-fast no longer runs CHANGED's three git commands.
- **Upgrade:** `/agent-harness:harness-upgrade` refreshes `harness.mk`, `red-proof.sh`, `.githooks/pre-commit` and `.githooks/pre-push` (unmodified copies). No repo-owned file changes; no migration.

## 2.0.11

Security fix, from a report on a repo using 2.0.8: `make test T=…` could run any command without a permission prompt.

- **T is data, not code.** harness.mk added `$(T)` to the recipe unquoted, and team settings usually pre-approve `Bash(make test:*)`. So `make test T='x; <cmd>'` (shell) and `make test T='$(shell <cmd>)'` (make expands command-line variables) both ran their payload unprompted, and check-fast did the same with changed file names. Now `override T := $(value T)` keeps T literal, and `test` exits 2 before any command when T holds anything but names, paths, `#method`, commas and globs (`[A-Za-z0-9_./#,*?:@+=[] -]`, no word starting with `-`). `CHANGED` leaves out file names outside `[A-Za-z0-9_.@+=,:/-]` or starting with `-`. T is still substituted at `{T}` or appended, so existing `HARNESS_TEST_ONE` values keep working.
- **Workspace `Makefile`:** `make test R= T=` and `make branch B= R=` pass their values to `ws.sh` as literal environment variables, no longer as shell text.
- **The Bash guard asks before `make` runs command-line code.** A pre-approved `make test:*` also matches `make test HARNESS_TEST_ONE='<cmd>'`. The guard now asks for any variable override except `T=` and dev-check's `RUN=`, for `--eval`, `-e`/`--environment-overrides` and `-f`/`--file`, and for `MAKEFLAGS`, `MAKEFILES` or `HARNESS_*` set in front of `make`.
- **Upgrade:** `/agent-harness:harness-upgrade` refreshes `harness.mk` (unmodified copies). Migration `make-args-literal`: fixes an unedited workspace `Makefile` automatically, and names a workspace `Makefile` with edited `ws.sh` recipes or a locally modified `harness.mk` as manual.
- Not changed: running tests runs repo code. An agent that can edit a test or the Makefile and run `make test` can still run anything; these fixes close the route that needed no file change.

## 2.0.10

Found on a Spring Boot/Maven repo: since init, `make test T=<class>` and check-fast's changed-test step exited 0 even with failing tests; a code review of the same repo found the sensor and setup bugs below.

- **Test arguments go where the command says.** `make test` appended `T` to `HARNESS_TEST_ONE`, and check-fast appended the changed files to `HARNESS_TEST_CHANGED`. Commands that can't take a trailing argument (Maven `-Dtest=`, Gradle `--tests`) ended in `; :` to swallow it, which also threw away the test's exit code: the targets were always green. Now a value containing `{T}` (or `{CHANGED}`) gets the argument substituted there and nothing appended; without a placeholder it is appended as before. The harness.mk header says a swallowing suffix must be `&& :`, never `; :`.
- **New: `scripts/harness/gate-proof.sh` proves the gate can fail.** In a scratch worktree it plants one trivial test beside an existing one (JUnit 5, pytest or Vitest/Jest). `test T=<it>` and check-fast must pass while it passes, then fail once it fails, and `test T=<no such test>` must fail. harness-init (step 5) and harness-upgrade (step 3) run it and record `gate_red_proven` in `.harness/init-state.json`. `harness-audit full` runs it too, and `level.py` reports a gate never proven red as a sensors gap (Robust tier).
- **harness-lint warns** when a `HARNESS_TEST_*` value in the Makefile (or its own `*.mk`) ends in `; :` or `;:`, continuation lines included.
- **0 tests ran is a failure.** The harness.mk Maven example and `layout.md` drop `-Dsurefire.failIfNoSpecifiedTests=false` from `HARNESS_TEST_ONE` and add a check that a surefire report from this run has `tests` > 0. A JUnit 4 class without the vintage engine, a missing `#method` or a typo now fails instead of passing. `layout.md` gives the equivalents: Gradle (`failOnNoMatchingTests`), pytest (exit 5), Jest/Vitest (no `--passWithNoTests`). `related-tests.sh` keeps `-DfailIfNoTests=false` for changed-files mode and passes the runner's exit code through, now covered by a self-test.
- **New: `scripts/harness/sensors/lib/diffscan.py`, one diff parser for sensors that check only new code.** Five sensor-smith sensors on the same repo each parsed `git diff -U0` by hand and repeated two bugs. An added line `++ x` shows as `+++ x`, which they took for a file header, skipping the rest of that file (a secret planted after it passed `make lint`). And a missing or shallow `HARNESS_BASE` made `git diff base...HEAD` exit 128, which they read as "no changes". `added_lines(base)` returns `{path: {lineno: text}}` for commits since the merge-base, staged and unstaged edits and untracked files, treats `+++ `/`--- ` as headers only before a file's first `@@`, and exits 2 with `sensor: cannot resolve HARNESS_BASE <ref>; fetch it or set HARNESS_BASE` when the base or merge-base can't be resolved. Shell sensors run it as a command (`path:lineno:text` lines). sensor-smith now builds on it, and registers such sensors with `"scope": "diff"`, for which `sensor-proof.sh` adds step 2b (each fixture file starts with an added `++ ` line; the sensor must still fire) and step 2c (an unresolvable `HARNESS_BASE` must fail loudly).
- **Setup no longer pushes its ports into a custom `setup-services`.** `setup.sh` exported each `*_PORT` it picked, and Docker Compose gives shell variables precedence over `--env-file`, so a repo's own services target that chose a different free port (and wrote it to `.env.local`) still bound the exported one ("port is already allocated"), or the app looked for a port nothing listened on. The services step now runs without those exports; migrate and seed get the ports re-read from `.env.local` afterwards.
- **Upgrade:** `/agent-harness:harness-upgrade` refreshes `harness.mk`, `lint.sh`, `setup.sh` and `sensor-proof.sh` (unmodified copies), installs `gate-proof.sh` and `sensors/lib/diffscan.py`, and runs the gate proof. Manual migrations: `test-exit-swallowed` names each `HARNESS_TEST_*` ending in `; :` (end it in `&& :` or use `{T}` / `{CHANGED}`), `gate-red` stays open until the gate proof passes, and `diff-sensors` names each sensor that parses `git diff` itself.

## 2.0.9

Fixes from running the harness on a Spring Boot/Maven repo.

- **Setup no longer asks for `~/.m2/settings.xml` when deps installed.** The "maven credentials" hint now appears only when `setup-deps` failed or was skipped, so a repo that passes `-s settings.xml` (or uses a registry extension) is not told to copy it.
- **Main checkout ports.** `make setup` kept the `.env.example` ports even when something else held them, so `docker compose up` failed with "port is already allocated". The main checkout now keeps an example port only while it is free or held by this compose project's own container; otherwise it gets a free port, recorded in `.env.local` (which wins on re-runs, as before).
- **Smoke reporting.** With `HARNESS_SMOKE` unset, setup printed `smoke ✓` although nothing ran; it now prints `smoke n/a`. Setup runs smoke only once nothing is listed under "needs you", and `HARNESS_SETUP_SMOKE = 0` keeps it out of setup entirely (for server apps whose smoke boots the app before the database is configured).
- **New: `make dev-check` / `make dev-stop`.** Set `HARNESS_HEALTH` (a URL or a command meaning "the app is up"). `dev-check` starts `make dev` in the background, waits up to `HARNESS_HEALTH_SECS` (120), runs `RUN='<cmd>'` if given, and always stops it (`scripts/harness/dev-check.sh`). Once it exists, the Bash guard refuses an agent's long-lived `make dev`, also when wrapped (`nohup`, `bash -c`, `VAR=`), and any run script listed in `HARNESS_DEV_BLOCK`. A repo that already defines its own `dev-check` keeps it, and the guard honours it.
- **One token count.** `level.py` counted characters and `lint.sh` bytes (≈2963 vs ≈3004 on the same files), so the audit's token check could pass while `harness-lint` warned. Both now use UTF-8 bytes / 4.
- **Less noise.** `harness-lint`'s check-fast warning only counts source files of the stacks whose build files the repo has, never `scripts/harness/` (a Maven repo's Python sensors were cited as untested). `HARNESS_TEST_CHANGED_CONFIRMED = 1` silences the custom-selector warning once you have checked the selector. `level.py --log` no longer appends a row identical to the last one.
- **Learning is offered at close.** `harness-session` Close gains step 5: when the session shows a repeated failure (the stop gate blocked twice on it or gave up, a FAIL or `Red: not proven` entry before the PASS, or a developer correction), it shows `Learn? <what happened> · seen <n>× · likely rung: …` and runs `harness-learn` only after the developer says yes. `harness-verify` now offers `harness-learn` the same way instead of running it unasked. Skill text only: nothing to upgrade in repos.
- **Upgrade:** `/agent-harness:harness-upgrade` refreshes `setup.sh`, `harness.mk` and `lint.sh` (unmodified copies) and installs `dev-check.sh`. Manual migration `dev-health`: a Makefile with `HARNESS_DEV` but no `HARNESS_HEALTH` (and no `dev-check` of its own) is asked to set it.

## 2.0.8

- **Test-first, proven.** New `scripts/harness/red-proof.sh`: in a scratch worktree with the current code, each changed test file must pass (green control), then fail once the changed production files are put back to the base (red). harness-verify's verifier runs it and records a `Red:` line in the evidence: `proven`, `n/a (<reason>)` (no production code changed, or a pure refactor/config change the verifier accepts), `not proven` (FAIL: write a test that fails first) or `inconclusive` (the tests can't run in a scratch worktree; the verifier tries by hand, else NEEDS-HUMAN).
- **Plans close only with a red proof.** `plan-check.sh fresh` (pre-commit, when a plan moves to `done/`) now also needs `Red: proven (…)` or `Red: n/a (<reason>)` in the latest PASS entry. Evidence written before 2.0.8 has no `Red:` line: run harness-verify again before closing an in-flight plan.
- **Templates and upgrade:** `INVARIANTS.md` → Testing gains "New or changed behaviour has a test that fails without the change" (migration `invariants-red-proof`, proposed for your yes); `AGENTS.md` Working Principle 4 now says test first. `/agent-harness:harness-upgrade` installs `red-proof.sh` and refreshes `plan-check.sh` (unmodified copies).

## 2.0.7

- **Fix: `harness-lint` failed on IDE/build copies of module `AGENTS.md`.** `lint.sh` found module `AGENTS.md` files with `find`, which did not skip build output. In a Maven repo an IDE build copied `src/main/java/.../AGENTS.md` into `target/classes/`, its relative links broke there, lint failed, and `level.py` measured the level as `none` after every build. `lint.sh` now lists candidates with `git ls-files -co --exclude-standard` (anything gitignored is skipped) and always drops `target/`, `build/`, `dist/`, `out/`, `.gradle/`, `node_modules/` and the tool folders; outside git it uses a pruned `find`. `scan.py` also skips `out/` and `.gradle/`.
- **Upgrade:** `/agent-harness:harness-upgrade` refreshes `scripts/harness/lint.sh` in repos with an unmodified copy. A repo that hand-patched its `lint.sh` for this bug (channelkart-api added `-not -path './target/*'`) shows it as `modified` and is not overwritten: take the upstream copy with `cp "<plugin>/skills/harness-init/assets/lint.sh" scripts/harness/lint.sh` (the upgrade report prints the `diff` command with the plugin path), then run the upgrade again so the manifest records it as current.

- Worktree subagents: when an implementer subagent stops with `check-fast` failing in its own git worktree, its branch is recorded in `.git/harness-red/`, and the Bash guard refuses to merge, cherry-pick or `pull .` it until a later stop there passes.
- `AGENTS.md` → Agent skills rule 8 for parallel and spec-driven flows (migration `agents-parallel`).
